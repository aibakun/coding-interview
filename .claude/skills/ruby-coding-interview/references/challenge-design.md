# 問題設計リファレンス

問題作成モードに入ったら、このファイルを読んでから題材を決める。

## 現在の基準難易度

出典は過去 2 回の演習記録 (インタビュー記録と作業ブランチの差分)。2026-09-19 時点で本リポジトリに Pull Request は存在しないため、PR が作られ始めたら `gh pr list --state all` と `gh pr view <番号> --comments` を優先の根拠にする。

| 軸 | 現在値 | 根拠 |
|---|---|---|
| 制限時間 | 45〜60 分 | 演習の固定条件 |
| ファイル数 | 2〜3 | 回 1 は 2 ファイルで読解に時間を要した |
| クラス数 | 2〜3 | 回 2 の 1 クラスは小さすぎ、設計判断の余地が乏しかった |
| スターターコード行数 | 100〜140 行 (上限 160) | 回 1 (約 90 行) で時間内に実装まで到達できなかったため、行数ではなく後述の難度軸で調整する |
| 主要な設計課題 | 1 個 | |
| 副次的な改善点 | 3 個 (2〜4) | 全部は直せない量にする |
| 既存テスト | 原則なし (利用者が特性テストを書く前提) | 挙動固定の練習が現在の重点 |

**現在の到達状況**: 特性テストを自力で書き、責務を 1 つ抽出するところまでは到達できる。到達できていないのは「洗い出した課題に優先順位を付けて、時間内に複数の改善を完了させる」段階。したがって当面は規模を上げるより、**優先順位判断が必要な構造**を強めること。

## 題材ログ (重複回避用)

新しい問題は、直近 2 回と **題材・主要課題・正解ムーブのどれも重ならない**ようにする。

| 回 | 日付 | 題材 | 規模 | 主要な設計課題 | 正解ムーブ |
|---|---|---|---|---|---|
| 1 | 2026-09-18 | ビデオレンタルのレジとレシート | 2 ファイル / 3 クラス / 約 90 行 | 1 つのメソッドに料金計算・ポイント計算・レシート整形・検証が同居 | 責務ごとのメソッド抽出、種別を表す整数定数の値オブジェクト化 |
| 2 | 2026-09-18 | ローン申込の一覧レポート | 1 ファイル / 1 クラス / 約 40 行 | 1 つのメソッドに抽出条件・料率・表示整形が同居 | 特性テストで固定してから行組み立てを抽出 |

新しい問題を出したら 1 行追加する。過去問のコードや仕様を転記しない (判断に必要なのはこの粒度まで)。

## 題材の重複を避ける 3 軸

次の 3 軸すべてで直近 2 回と差を付ける。1 軸でも一致したら選び直す。

1. **題材ドメイン** — 使用済み: 小売レジ・レンタル課金 / 申込一覧レポート。未使用の例: 在庫と補充、予約と枠管理、シフトと勤怠、配送料と配送区分、サブスクの更新と解約、権限とアクセス判定、CSV 取込のバリデーション。
2. **主要な設計課題の型** — 使用済み: 長いメソッドへの責務同居 (2 回連続)。未使用の例:
   - 条件分岐の重複 (同じ分岐が複数箇所に散っている)
   - データと振る舞いの分離 (計算ロジックが呼び出し側に漏れている)
   - 原始データ型への執着 (金額・期間・区分が裸の数値や文字列)
   - 依存の向きの誤り (下位の都合が上位に漏れている、現在時刻や標準出力への直接依存)
   - 状態の持ちすぎ (可変な属性が多く不変条件が守られない)
3. **正解ムーブ** — 使用済み: メソッド抽出 / 特性テスト → 行組み立ての抽出。未使用の例: ポリモーフィズムで分岐を置換、値オブジェクトの導入、コレクション操作を Enumerable へ置換、引数をキーワード引数と既定値で整理、依存を引数で注入して外部要因を切り離す。

## 問題設計の判断基準

**満たすべきもの**

- 業務仕様として自然に読める。「なぜこう書かれたか」に業務的な理由が想像できる
- 実行すると意味のある出力が出る。出力を `diff` で比較して挙動固定できる
- 主要課題を直せば副次課題の一部が自然に解消する構造になっている (優先順位に正解らしさが生まれる)
- 副次課題のうち少なくとも 1 つは「気付いても後回しにすべき」もの (命名の細かい揺れ、使われていない引数など)
- 仕様に 1〜2 箇所だけ曖昧さを残し、面接官への質問が有効に働くようにする
- スターターコードは実行可能で、最初から壊れていない

**避けるもの**

- 出力全体がランダム性や現在時刻で毎回変わる (挙動固定ができなくなる)。時刻依存を設計課題として出す場合は、変動する出力を 1 行に閉じ込め、その行を除けば `diff` で比較できる形にする
- 外部ネットワーク・DB・gem への依存 (原則 Pure Ruby、標準ライブラリのみ)
- 汚さのための汚さ (意味のないワンライタ、無意味な変数名の羅列)
- 1 つの正解しかない書き換え。複数の妥当な設計が成り立つようにする
- 読解だけで 20 分を超える分量

## 難易度の上げ下げ

**コード量では調整しない。** 次の軸で上下させる。

| 難度軸 | 下げる | 上げる |
|---|---|---|
| 業務ルール | 独立したルールが並ぶ | ルールどうしが影響し合う (割引と付与率が互いに依存、適用順序で結果が変わる) |
| 分岐 | 1 箇所に集約されている | 同じ判定が 2〜3 箇所に散っている |
| 依存 | 入出力が引数と戻り値で閉じている | 現在時刻・標準出力・グローバルな設定への直接依存が混じる |
| 境界 | 入力が正常系のみ | nil・空配列・想定外の区分値が混じる |
| 優先順位 | 副次課題 2 個 | 副次課題 4 個 + 時間内に全部は直せない配置 |
| 仕様 | 問題文に全て書いてある | 一部は質問しないと確定しない |
| 変更範囲 | 1 クラス内で閉じる | クラスをまたいで責務を移す必要がある |

## 問題作成チェックリスト

- [ ] `git log --all --stat`、`git stash list`、既存の問題ディレクトリ、`gh pr list --state all` を確認した
- [ ] 題材・主要課題・正解ムーブの 3 軸すべてが直近 2 回と異なる
- [ ] ファイル数 2〜4、クラス数 2〜4、全体で 80〜160 行に収まっている
- [ ] 主要な設計課題が 1 つ、副次的な改善点が 2〜4 個ある
- [ ] 全部を直すには時間が足りない配置になっている
- [ ] 出力が決定的で、`diff <(ruby before.rb) <(ruby after.rb)` 相当の比較ができる
- [ ] `ruby <エントリファイル>` が正常終了する (実行確認はここまで。解かない)
- [ ] 問題文に背景・現在の仕様・依頼・実行方法・制限時間・完了時に説明してほしい内容がある
- [ ] 問題文に模範解答・推奨構成・抽出すべきメソッド名・スメルの答え・優先順位・採点基準・ヒントが含まれていない
- [ ] 既存の命名規則に従っている (なければ構成を提案して合意を取った)
- [ ] 過去の問題・回答を変更していない
- [ ] 題材ログに 1 行追加した

## リポジトリの実行環境メモ

- Ruby 3.3.1、RSpec 3.13 が利用可能
- `.rspec` は `--default-path .` のため、リポジトリ直下を起点に spec を探す
- `.zed/tasks.json` に「現在のファイルを `ruby` で実行」「現在のファイル/行を `rspec` で実行」「ルートの `main.rb` を実行」がある。問題のエントリファイル名と実行コマンドは問題文に明記する
- 過去の作業はリポジトリ直下にフラットに置かれていた。ディレクトリ構成の規則は未確定なので、最初に構成を決めるときは利用者に確認する
