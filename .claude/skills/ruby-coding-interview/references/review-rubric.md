# レビュールーブリック

レビューモードに入ったら、このファイルを読んでから評価を書く。

## 前提

- 判断の根拠は**実際のコードと差分**に置く。「読みやすくなりました」のような感想だけで終わらせない
- 模範解答を唯一の正解として扱わない。別の設計を選んでいる場合は、その意図とトレードオフを聞いた上で評価する
- **未実装の理想形より、制限時間内に安全な改善を完了させたことを重視する**
- 面接官がヒントを出していた場合は、その段階数を踏まえて割り引く

## 収集する材料

| 材料 | 取得方法 |
|---|---|
| 変更差分 | `git diff`、`git log -p`、`git stash list` (未コミットの作業も見る) |
| 実行結果 | 改善前後の出力比較。利用者が `diff <(ruby before.rb) <(ruby after.rb)` 相当を行ったか |
| 追加テスト | spec ファイルの有無、何を固定しているか、改善前に書かれたか |
| コミット/PR | コミットの粒度とメッセージ、`gh pr view <番号> --comments` |
| 実装方針 | 利用者の説明。無ければ「なぜこの順で直したか」を先に聞く |
| 過去からの改善 | 前回の More が今回どうなったか |

## 評価観点と判断基準

### 1. 既存挙動を担保できているか

- **Good**: 変更前に出力を保存するか特性テストを書いてから着手した。比較を人の目視ではなく `diff` やテストで自動化した。境界 (nil、空、想定外の区分値) を固定対象に含めた
- **More**: 出力の目視確認だけで進めた。テストが改善後に書かれた。テストが 1 ケースに全期待値を詰め込んでいて、壊れた箇所が特定できない

### 2. 本質的な問題を見つけられているか

- **Good**: 保守性を最も下げている箇所を主要課題として名指しできた。副次課題との重要度の差を説明できた
- **More**: 命名やフォーマットなど影響範囲の小さい点に時間を割いた。課題を列挙しただけで重み付けがない

### 3. 限られた時間で優先順位を付けられているか

- **Good**: 洗い出し後に「今日やる/やらない」を明示的に線引きした。やらないと決めた理由を言える
- **More**: 全部直そうとして手が止まった。優先順位を付けずに着手した

### 4. 小さく安全に変更しているか

- **Good**: 1 つの意図につき 1 ステップ。各ステップ後に実行またはテストで確認している。コミットが分かれている
- **More**: 広範囲を一度に書き換えた。動作確認の間隔が長い。抽出と仕様変更が 1 つの変更に混ざっている

### 5. 実際に動くところまで完了しているか

- **Good**: 制限時間終了時点でコードが動き、改善が反映されている
- **More**: 分析・方針の言語化で終わった。途中状態で壊れたまま終わった

### 6. Ruby として読みやすいか

- **Good**: `Enumerable` (`map` / `select` / `sum` / `group_by` など) を適切に使う。キーワード引数で呼び出し側の意味が読める。早期 return とガード節。定数や値オブジェクトでマジックナンバーを消している
- **More**: 抽出はしたが、抽出先に三項演算子や長い式を詰め込んで 1 行が読めない。`each` + 手動の蓄積変数のままにしている。意味のない略語名。金額計算に浮動小数を使っている

### 7. 責務と依存関係が改善されているか

- **Good**: 計算・判定・表示が分離した。データを持つ側に振る舞いが移った。外部要因 (時刻、標準出力) への依存が切り離された
- **More**: メソッドは分かれたが、分けた先が同じ呼び出し元の事情を知ったままで結合が減っていない。private メソッドが増えただけでクラスの責務は変わっていない

### 8. 変更理由と残課題を説明できるか

- **Good**: 「何を直し、何を直さず、次に何をやるか」を根拠付きで言える。採らなかった設計案とその理由も言える
- **More**: 「きれいにしました」以上の説明がない。残課題を把握していない

### 9. 時間の使い方が適切か

下の目安と実際のタイムラインを突き合わせる。

| フェーズ | 目安 (60 分の場合) |
|---|---|
| 読解・実行・仕様質問 | 〜10 分 |
| 挙動固定 (出力保存またはテスト) | 〜15 分 |
| 課題洗い出しと優先順位付け | 〜20 分 |
| 改善の実装 (小さく反復) | 〜50 分 |
| 最終確認・説明の整理 | 〜60 分 |

- **Good**: 最初のコード変更が 25 分以内に始まっている。終了 10 分前に手を止めて確認と整理をしている
- **More**: 分析が 30 分を超えた。最後まで実装を続けて確認時間が残らなかった

## Good / More の書き方

- Good は「やった行動」を書く。人格や姿勢ではなく行動を褒める (「理解しようとする姿勢が良い」より「着手前に実行して出力を保存したのが良い」)
- More は**次回の具体的な行動**に変換する。「優先順位を付けましょう」ではなく「洗い出し後に 2 分使って、やる 2 件とやらない 3 件を書き出す」
- Good と More はそれぞれ 2〜4 件。多すぎると次回に効かない
- 「コード上の具体的なフィードバック」ではファイル名と該当箇所を引用し、改善案を Ruby コードで示す。**このセクションだけは具体的な書き換え例を出してよい** (レビュー後なので伏せる必要がない)

## 継続テーマ (過去のレビューから)

毎回ここを確認し、改善していれば Good に、変わっていなければ More に書く。解消したらこの一覧から外し、新しいテーマに置き換える。

1. **分析過多**: 課題の洗い出しは得意だが、そこで時間を使い切って実装に入れない
2. **挙動固定の自動化**: 出力の目視確認ではなく `diff` やテストで担保する
3. **優先順位付け**: 洗い出した課題に重み付けし、時間に対して現実的な範囲を選ぶ
4. **抽象と具体の往復**: 「違和感がある」で止めず、具体的な Ruby コードの形まで落とす
5. **Step by Step**: 完璧を目指さず、保守性を最も下げている箇所から小さく直す

## 次回難易度への反映

レビューの最終セクションで次回の調整を宣言し、`challenge-design.md` の「現在の基準難易度」と「題材ログ」を更新する。

| 今回の結果 | 次回の調整 |
|---|---|
| 挙動固定が素早く、主要課題を選べ、60 分以内に改善を完了し、構文で詰まらず、理由を説明できた | 難度軸を 1〜2 個上げる (ルールの相互作用、分岐の分散、依存の向き、副次課題を 4 個へ) |
| 実装は完了したが優先順位の判断が甘い | 規模は据え置き、副次課題を増やして「全部は直せない」圧を強める |
| 挙動固定はできたが改善が 1 件で終わった | 規模を下限寄り (2 クラス / 100 行) にして、完了体験を優先する |
| 分析で時間を使い切った、実装が完了しなかった | 難度を下げる。ルール数と分岐の絡みを減らし、曖昧さを排して読解時間を削る |
| 大きく書き換えて挙動を壊した | 規模据え置きで、挙動固定が効きやすい題材 (出力が決定的で境界が明確) を選ぶ |
| Ruby の基本構文で頻繁に止まった | 難度を下げ、`Enumerable` やキーワード引数など特定の基本機能が自然に必要になる題材にする |

**コード量を増やす方向では調整しない。**
